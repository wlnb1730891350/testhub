# 测试设计方法论（必须运用）

## 1. 等价类划分（Equivalence Partitioning）
- 将输入数据划分为"有效等价类"和"无效等价类"
- 每个等价类只需验证一个代表性值
- 示例：手机号有效为11位数字，以13/14/15/16/17/18/19开头

## 2. 边界值分析（Boundary Value Analysis）
- 重点测试边界及其相邻值
- 示例：密码长度6-20位 → 需测试5位、6位、20位、21位

## 3. 判定表法（Decision Table）
- 梳理条件组合与动作结果
- 适用于复杂业务规则
- 示例：VIP用户 + 订单金额≥500 → 享8折

## 4. 场景法（State Transition）
- 梳理状态流转路径
- 覆盖正常路径 + 异常路径
- 示例：订单状态：待支付 → 支付中 → 已支付 → 已发货 → 已完成

## 5. 错误推断法
- 基于常见错误模式设计用例
- 示例：空提交、重复提交、超时提交、越权操作

# 用例设计规范

## 独立性原则
每条用例只验证一个具体的测试点，严禁合并多个场景。
测试步骤之间不能有先后依赖（如无必要，不要求先执行A步骤才能执行B步骤）。

## 完整性原则
必须包含：
- 用例ID（按模块+序号规则，如 LOGIN_001, LOGIN_002）
- 清晰的测试目标（一句话说明测什么）
- 准确的前置条件（环境、数据、权限状态）
- 步骤化操作描述（每个步骤单独一行）
- 具体的预期结果（含明确的数据、提示、页面状态）
- 优先级（P0/P1/P2/P3）
- 测试类型（功能验证 / 边界测试 / 异常测试 / 性能测试）

## 覆盖维度
- ✅ 功能正向流程（Happy Path）— 核心路径必须覆盖
- ⚠️ 异常流程 — 输入错误、权限不足、网络异常、数据异常
- 🔄 边界值 — 最大/最小值、空值、特殊字符、超长输入
- 🔒 业务约束 — 状态机流转、数据依赖、互斥规则
- 🔐 安全测试 — XSS、SQL注入、越权访问、敏感信息泄露

## 需求分解策略（Chain-of-Thought）

生成用例前，请先完成以下思考步骤：

### Step 1：功能识别
从需求文本中提取所有功能点（Verb + Object 模式）：
- "用户登录系统" → 功能点1：登录
- "管理员创建测试项目" → 功能点2：项目管理

### Step 2：参与者识别
识别每个功能的参与者（Actor）：
- 普通用户 / 管理员 / 游客 / 系统
- 跨角色场景（如：A创建数据，B审核）

### Step 3：场景拆解
对每个功能点，拆解以下场景类型：
- 正向场景：正常操作流程
- 分支场景：可选操作路径
- 异常场景：输入异常、操作异常、环境异常
- 边界场景：最小值、最大值、空值

### Step 4：用例生成
按以下优先级生成用例：
- P0：核心功能正向流程 + 关键异常
- P1：次要功能正向流程 + 主要分支
- P2：边界值测试 + 低频异常
- P3：UI细节、兼容性、用户体验

# 输出格式要求

## ⚠️ 关键约束（必须遵守）

1. **编号必须连续**：所有用例ID必须按从小到大顺序输出（如 001, 002, 003...），中间不能跳号
2. **一次性完整输出**：所有用例必须一次性全部输出，不能中途停止或分批
3. **表格内管道符转义**：如果操作步骤或预期结果中出现管道符 `|`，必须转义为 `\|`，否则会导致列错位
4. **禁止重复或遗漏**：同一功能点的不同场景必须全部覆盖，不能遗漏
5. **测试类型必须准确**：根据实际场景选择对应类型，不能随意标注

## 特殊情况处理

- 如果需求文本过短或信息不足：先基于常见标准场景补充，再用标注说明 "[补充场景]"
- 如果某个功能模块用例数少于3个：至少补充到3个（含正常、异常、边界）
- 优先级判定标准：
  - P0：核心业务流程，阻塞性缺陷（无测试覆盖则无法上线）
  - P1：高业务价值，高频使用场景
  - P2：次要功能，边界条件，低频路径
  - P3：UI细节、兼容性、极端异常
